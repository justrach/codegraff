## 2. `GraffServeClient.swift` — The NDJSON Protocol Client

### Transport contract
- The client implements the **local `serve` transport** described in `architecture.md` and the TS/Python SDKs (`sdk/ts/remote.ts`, `sdk/py/harness_sdk.py`).
- Two HTTP calls are required per turn:
  1. `POST /v1/sessions` → returns `{session_id}` (`GraffServeClient.swift:47`).
  2. `POST /v1/sessions/{id}` with a JSON payload `{"type": "user", "text": text}` → streamed back as **NDJSON** (one JSON object per line) until a terminal event (`turn` or `error`) (`GraffServeClient.swift:57`).

### Request builder
- `base` defaults to `http://127.0.0.1:8787` (`GraffServeClient.swift:25`).
- Always sends `Content-Type: application/json` and `User-Agent: Graff-iOS/0.1` (`GraffServeClient.swift:33`). The comment explicitly states the UA is required because *"CF WAF rejects empty UA on the gateway path"*.
- Optional bearer token: `Authorization: Bearer <token>` (`GraffServeClient.swift:34`).

### Event decoding
- `GraffEvent` enum (`GraffServeClient.swift:4`) covers:
  - `.reasoning(String)`
  - `.text(String)`
  - `.toolCall(name: String)`
  - `.turn(text: String, contextTokens: Int, costUSD: Double)`
  - `.error(String)`
  - `.other(String)` (fallback for unknown types)
- `decode(_:)` (`GraffServeClient.swift:82`) uses `JSONSerialization` to parse each line and switches on the `type` field:
  - `reasoning`, `text`, `tool_call`, `turn`, `error` are mapped explicitly.
  - Anything else becomes `.other(type)`.

### Streaming implementation
- `streamTurn(sessionID:text:)` returns an `AsyncThrowingStream<GraffEvent, Error>` (`GraffServeClient.swift:57`).
- It uses `URLSession.shared.bytes(for:)` to get an `AsyncBytes` sequence, iterates `bytes.lines`, and yields decoded events.
- **Termination rules**: it stops yielding and finishes the stream when it encounters either `.turn` or `.error` (`GraffServeClient.swift:69-70`).
- Cancellation is wired up: `continuation.onTermination` cancels the `Task` reading the bytes (`GraffServeClient.swift:77`).

### Inferred design note
A code comment (`GraffServeClient.swift:23`) states: *"The `cube` transport is this same client with a different base URL + a tenant capability header."* The current struct only has `base` and `token`; the capability header is not yet implemented.

## 3. Main UI: `ChatView.swift` & `SessionsListView.swift`

### `SessionsListView` — Root navigation
- Wraps a `NavigationStack` containing a `List` of `NavigationLink`s (`SessionsListView.swift:3`).
- Each row is bound to an `AgentSession` via `ForEach($sessions)` and pushes `ChatView(session: $session)` on tap.
- `SessionRow` (`SessionsListView.swift:28`) displays:
  - Title + `StatusChip` (tinted capsule with SF Symbol).
  - Model name, todo progress (`done/total`), and `lastActivity` timestamp.
  - A `ProgressView` tinted to the session status.
- The toolbar has a `+` button (no-op implementation: `Button { }`).

### `ChatView` — Session detail
- Takes `@Binding var session: AgentSession` and an optional `autoSend: String?` (`ChatView.swift:3`).
- **Layout** (top to bottom):
  1. `TaskProgressCard` — shows todos with status symbols, pulse animation on `.inProgress`, and strikethrough for completed items (`ChatView.swift:106`).
  2. `ScrollViewReader` + `ScrollView` with `LazyVStack` of `MessageBubble`s. Auto-scrolls to the last message when its text changes (`ChatView.swift:23`).
  3. `PlanDecisionBar` — shown conditionally when `session.planPending` is true; has "Keep planning" and "Implement plan" buttons (`ChatView.swift:185`).
  4. `Composer` — multiline `TextField` (axis `.vertical`, line limit 1…4) plus send button; disabled while `streaming` is true (`ChatView.swift:205`).

### `MessageBubble` & assistant states
- `MessageBubble` (`ChatView.swift:136`) left/right aligns based on role.
- If `message.reasoning` is present, it shows a `Label` with `systemImage: "brain"` in caption italic style.
- If the assistant message text is empty and reasoning is empty, it renders a `TypingIndicator` (three pulsing dots) so an in-flight turn never looks like a stuck empty bubble (`ChatView.swift:167`).

### Turn lifecycle (`send` → `runTurn`)
- `send()` (`ChatView.swift:64`) appends a user `ChatMessage`, sets `streaming = true`, `session.status = .working`, and kicks off `runTurn` in a `Task`.
- `runTurn(_:)` (`ChatView.swift:75`) is `@MainActor`:
  - Lazily creates a remote session via `client.createSession(model: session.model)` if `serveSessionID` is nil.
  - Appends a blank assistant message.
  - Iterates `client.streamTurn` and mutates the message in place:
    - `.reasoning` appends to `message.reasoning`.
    - `.text` appends to `message.text`.
    - `.turn` overwrites `message.text` with the final text.
    - `.error` sets `message.text` to `"Error: " + m`.
    - `.toolCall` and `.other` are ignored (`break`).
  - On catch, appends a transport error message.
  - Always sets `session.status = .idle` in `defer { streaming = false }`.

### Inferred design note
`ChatView` is purely optimistic/in-memory: there is no CoreData, no SwiftData, no file persistence. Session state survives only while the view hierarchy retains it.

## 4. Connection to the Core Harness, Data Streamed, and Protocol Handling

### How it connects
- The iOS app targets `http://127.0.0.1:8787`, which is the default address of `graff serve` (or `harness serve`) running on the host Mac.
- Because the iOS simulator shares localhost with the host, `127.0.0.1:8787` from the simulator reaches the host's serve process (`GraffServeClient.swift:20` comment).

### What data streams
- **Request** (turn): `{"type": "user", "text": "<prompt>"}`.
- **Response**: NDJSON lines, each a JSON object. The iOS client specifically handles:
  - `reasoning` → shown in the bubble as a brain-labeled italic caption.
  - `text` → appended to the assistant bubble.
  - `turn` → final text + metadata (`context_tokens`, `cost_usd`). The client replaces the bubble text with the final `turn.text`.
  - `error` → displayed as `"Error: ..."`.
  - `tool_call` → **ignored** (`ChatView.swift:97`).

### Protocol handling characteristics
- **Session-oriented**: A `serveSessionID` is created once per `ChatView` and reused for subsequent turns.
- **Terminal-event driven**: The stream ends on `.turn` or `.error`. This matches the Python/TS SDK behavior (`sdk/py/harness_sdk.py:447`, `sdk/ts/remote.ts:165`).
- **No interactive tool loop**: Unlike the Python/TS SDKs, the iOS client does not currently handle `ask_user` or multi-step `tool_call` / `tool_result` cycles. It treats the stream as a single-turn text response.
- **NDJSON parsing**: Uses `JSONSerialization` (not `Codable`) for line-by-line decoding, which is tolerant of unknown fields.

### Verified cross-reference
The architecture document (`architecture.md`) describes the core harness as a Zig REPL/agent that can run in `--json` mode (stdio) or `serve` mode (HTTP). The iOS client consumes the *serve* bridge, where each session is a real `harness --json` child and one POST equals one protocol request, streamed back as NDJSON (`sdk/ts/remote.ts:8` comment).

## 5. Build / Automation Scripts

### `build-sim.sh` (`apps/ios/build-sim.sh`)
- **No Xcode required**. Compiles the app directly with `swiftc` for the iOS simulator.
- Key steps:
  1. Sets `TARGET=arm64-apple-ios26.0-simulator` and fetches the iPhoneSimulator SDK path via `xcrun`.
  2. `rm -rf build && mkdir -p build/Graff.app`.
  3. Compiles `Graff/Sources/*.swift` into `build/Graff.app/Graff` with `-emit-executable`.
  4. Copies `Info.plist` into the app bundle.
  5. Boots the simulator (`xcrun simctl boot`), opens the Simulator app.
  6. Installs and launches the bundle (`com.codegraff.graff`).
  7. Waits 4 seconds and screenshots `build/launch.png`.
- Default device is `iPhone 17 Pro`, overridable via `SIM` env var.

### `autotest.sh` (`apps/ios/autotest.sh`)
- **Smoke test for the live transport**.
- Terminates any running instance of the app, then launches it with `--autotest`.
- Waits 16 seconds for the auto-fired turn to complete.
- Captures a screenshot to `build/autotest.png`.
- Used to verify the full stack (simulator → `graff serve` → NDJSON stream → UI) without human interaction.

### `recap.sh` (`apps/ios/recap.sh`)
- **Multi-stage screenshot capture for documentation/demos**.
- Launches with `--autotest`, then takes three timed screenshots:
  - `sleep 5` → `build/cap_typing.png` (should catch the `TypingIndicator` while waiting for the first token).
  - `sleep 3` → `build/cap_mid.png` (partial stream).
  - `sleep 8` → `build/cap_reply.png` (final response).
- These screenshots are likely the ones referenced in the repo (existing `build/cap_*.png` files).

## 3 Load-Bearing Facts

1. **`GraffServeClient` consumes the serve NDJSON stream via `AsyncThrowingStream`, terminating on `.turn` or `.error` events, and decodes only a subset of the full harness event contract** (`GraffServeClient.swift:57-82`, `ChatView.swift:75-104`).
2. **The entire build/install/run cycle is scriptable without Xcode** (`build-sim.sh` compiles with `swiftc`, `autotest.sh` gates the live transport, and `recap.sh` captures demo screenshots), making the iOS app a lightweight CI-verified frontend.
3. **The iOS app is a thin, in-memory client with no persistence layer**: sessions are hardcoded (`sampleSessions`), state lives in `@State`/`@Binding`, and the connection is to `127.0.0.1:8787` on the host Mac via the simulator's shared localhost (`GraffApp.swift:111`, `GraffServeClient.swift:25`, `Info.plist` local-network exception).
