## 2. Sessions (`sessionStore`, `SessionProvider`, `useSession`, `sessionClientActions`)

### 2.1 Store (`gui/src/app/sessionStore.ts:1`)
- Built on **Zustand vanilla** (`createStore`), not React context, for performance.
- Core state shape (`SessionStoreState`):
  - `selection: WorkspaceBoardSelection` — what the board shows (`empty`, `single-chat`, `workspace-draft`, `saved-workspace`).
  - `workspaces`, `workspacesByPath`, `conversationSummariesByKey`, `conversationViewsByKey`.
  - `promptDraftsByKey`, `attachmentsByKey`, `workspaceMetaByKey` (runtime status + prompt settings).
  - `requestTimingsByConversationId` — tracks start/completion times per request.
- `applySessionSnapshot(snapshot)` is the primary reducer: it rebuilds `conversationViewsByKey`, `conversationSummariesByKey`, updates `selection`, and computes request timings by diffing `activeRequestIds` (`sessionStore.ts:315`).
- Memoized helper selectors (`getUiActiveWorkspacePath`, `getUiActiveConversationId`, `getUiActiveBinding`) respect the `selection` override vs. the snapshot’s `activeWorkspacePath`/`activeConversationId`.

### 2.2 `SessionProvider` (`gui/src/app/SessionProvider.tsx:1`)
- Wraps children in `SessionActionsContext.Provider` with a memoized `actionState` object containing ~20 async actions.
- Key actions:
  - `openWorkspaceByPath` — calls `desktopClient.openWorkspace`, then `applySessionSnapshot` + `syncBoardSelectionFromSnapshot`.
  - `selectConversation` — optimistic UI update (`setBoardSelection`), then fetches snapshot via `desktopClient.selectConversation`, with revert on failure.
  - `startNewChat` — reuses a “managed chat” draft if available, otherwise creates a new one.
  - `submitPrompt` — reads the draft from `sessionStore`, appends attachments, clears draft, calls `desktopClient.sendPrompt`, then migrates the draft/attachments to the new conversation key.
- Bootstrapping: `useSessionBootstrap` (`gui/src/hooks/useSessionBootstrap.ts:1`) is used inside `SessionProvider`:
  - Listens to `SESSION_UPDATED_EVENT_NAME` (`codegraff://session-updated`).
  - Fetches `getSessionSnapshot`; if no active workspace, restores the latest from `localStorage` (`LATEST_WORKSPACE_STORAGE_KEY`), or falls back to `createManagedChat`.

### 2.3 `useSession` hook (`gui/src/hooks/useSession.ts:1`)
- Thin Zustand selectors over `sessionStore`.
- `useConversationSession(binding?)` returns:
  - `messages`, `activeRequestIds`, `requestTimingsById`, `followupRequest`, `todos`, `workspacePath`, `isConversationLoading`, `activeWorkspaceConfigured`, etc.
- `usePromptDraft(binding?)` returns draft state + `canCompose` (blocked by unconfigured workspace, pending followup, pending draft, or running conversation).
- `useWorkspaceMeta(workspacePath)` auto-fetches `runtimeStatus` and `promptSettings` on mount via `ensureWorkspaceRuntimeStatusLoaded` / `ensureWorkspacePromptSettingsLoaded`.

### 2.4 Client actions (`gui/src/app/sessionClientActions.ts:1`)
- Thin async wrappers around `desktopClient` calls that also update `sessionStore` after success.
- Examples: `runWorkspaceRuntimeStatusAction`, `updateWorkspacePromptSettings`, `submitFollowupResponse`, `openWorkspaceInTarget`.

## 3. Chat / Activities Rendering

### 3.1 `ChatThread` (`gui/src/components/chat/ChatThread.tsx:1`)
- Uses `@legendapp/list/react` (`LegendList`) for virtualized rendering of `ChatThreadItem[]`.
- **Auto-scroll logic:** tracks `isFollowingRef` / `userWantsFollowRef`. Locks to bottom while `isFollowing` is true; user scroll-up breaks the lock and shows a “Scroll to latest” pill with `pendingCount` of new items.
- Items are built by `buildChatThreadItems(messages, activeRequestIds)` (`gui/src/components/chat/utils/chatThread.ts:1`).

### 3.2 Thread item builder (`gui/src/components/chat/utils/chatThread.ts:1`)
- Walks `TranscriptMessage[]` and groups tool calls into `ActivityItem` groups scoped by `requestId` + scope index.
- Message kinds handled:
  - `user` / `context_compacted` → message item + starts a new scope.
  - `assistant` / `error` → message item.
  - `reasoning` → merged into a “Thinking” activity group.
  - `tool_start` → operation pushed into current group.
  - `status_output` → appended to the latest open operation’s `outputText`.
  - `tool_end` → marks operation completed, sets `isError`, `summary`, `resultDetail`.
  - `status` → displayed as standalone message (unless decorative debug).
- Final pass inserts `request_work` items after their anchor message.

### 3.3 `ChatActivityRow` (`gui/src/components/chat/ChatActivityRow.tsx:1`)
- Renders each `ActivityItem` inside a `Collapsible`.
- If `isThinking`, shows a “Thinking” label with optional reasoning text rendered as `ChatMarkdown`.
- Otherwise shows a summary label (e.g., “Explored 3 files”, “Ran 2 commands”) and a list of `ActivityOperationRow`.
- Auto-opens on running→idle transition if error; preserves user-open state otherwise.

### 3.4 `ActivityOperationRow` (`gui/src/components/chat/ChatActivityRow.tsx:115`)
- Maps `operation.detail.kind` to icons (`file_read`, `file_update`, `shell`, `search`, `fetch`, `plan`, `skill`, `task`, `todo_*`, `unknown`).

### 3.5 Activity results (`gui/src/components/chat/activity-results/ActivityResultRenderer.tsx:1`)

### 4.2 Chat tile (`ChatTile.tsx:1`)

- **Constraints:** `applyChatTileLayoutConstraints` locks group headers; `autoCloseUndersizedSidePanes` closes side panes dragged below 180px.

### 4.3 Layout utilities (`gui/src/components/workspace-board/layout.ts:1`, `chatTileLayout.ts:1`)

## 6. State Management Patterns & Tauri Backend Bridge

### 6.1 Frontend → Backend
- **Single service file:** `gui/src/services/desktop/client.ts:1` wraps every Tauri command.
- Uses `invoke<T>(command, args)` from `@tauri-apps/api/core`.
- **QA mock mode:** When `import.meta.env.VITE_CODEGRAFF_QA_MOCK === "1"`, `client.ts` short-circuits to deterministic mock snapshots/responses so the UI can be tested in a browser without Tauri.

### 6.2 Backend → Frontend (events)
- `listenSessionUpdates` listens to `codegraff://session-updated` (`emitter.rs:1`).
- `listenTerminalOutput` / `listenTerminalExit` / `listenTerminalErrors` listen to terminal-specific events.
- `TauriEventEmitter` (`emitter.rs:20`) implements `UiEventEmitter` and pushes `SessionSnapshotDto`, `TerminalOutputEventDto`, etc. into the webview via `tauri::Emitter`.

### 6.3 Backend runtime (`gui/src-tauri/src/runtime/simple.rs:1`)
- `RuntimeManager` coordinates the GUI with a persistent `graff --json` child process per conversation.
- **Session lifecycle:** `acquire_session_io` spawns `graff --json --yolo` (with login-shell env injection for macOS); reuses the child across turns; drops it on `stop_prompt` or error.
- **Streaming protocol:** `stream_turn` reads JSONL events from `graff` stdout:
  - `text` → `Assistant` message (appended live).
  - `reasoning` → `Reasoning` message.
  - `tool_call` / `tool_result` → `ToolStart` / `ToolEnd`.
  - `ask_user` → creates a `FollowupRequestDto` and stores it in `pending_followups`; UI renders via `followup` in conversation view.
  - `error` / `turn` → ends the turn.
- After each event, `emit()` calls `snapshot()` and pushes the full `SessionSnapshotDto` to the frontend, which then `applySessionSnapshot`s it.

### 6.4 Persistence (backend)
- Conversations are persisted to `~/.codegraff-gui/conversations.json` (`simple.rs:1582`).
- Prompt settings (model/effort/fast) persisted to `~/.codegraff-gui/prompt-settings.json`.
- Saved workspace layouts and conversation layouts stored via `ProjectStore` (`project_store.rs`).

## 3 Load-Bearing Facts

1. **The entire frontend state is reconciled from backend-issued `SessionSnapshot` DTOs.** The `sessionStore` does not optimistically update messages; it only updates `promptDrafts` and `selection` locally. Every streaming token arrives via Tauri event → `applySessionSnapshot`, which rebuilds `conversationViewsByKey` and timing maps (`sessionStore.ts:315`). This means the frontend is essentially a reactive projection of the backend `RuntimeManager` state.

2. **`WorkspaceBoard` selection state determines the Dockview outer layout, not the other way around.** The board reacts to `selection` (empty / single-chat / saved-workspace) by resetting or restoring the outer Dockview. When the user drags a chat panel in a saved workspace, the layout JSON is serialized and sent back to Tauri (`desktopClient.updateSavedWorkspaceLayout`), and the active chat binding is updated in the store (`WorkspaceBoard.tsx:127`).

3. **The backend spawns a persistent `graff --json` child per conversation and streams JSONL events into `SessionSnapshotDto`s that are pushed to the frontend.** This is the primary bridge: commands are RPC via `invoke`, and live updates are events via `emit_session_updated`. The frontend has no WebSocket or SSE; it relies entirely on Tauri’s `invoke` + `listen` abstraction.

## 1 Open Question

- **How does the frontend handle backpressure or out-of-order `session-updated` events?** The `useSessionBootstrap` hook sets `receivedSessionUpdateRef` to avoid overwriting a newer event with an older snapshot during bootstrap, but there is no explicit sequence numbering or debouncing in `sessionStore.applySessionSnapshot`. If two events arrive close together, the Zustand store will apply both in order, but React components may re-render with intermediate states. Is this acceptable because the backend only emits snapshots sequentially from a single `RuntimeManager` mutex, or should the frontend add a generation/version counter to drop stale snapshots?
