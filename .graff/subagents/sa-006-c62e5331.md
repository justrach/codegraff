# Zig Core Report: `simple-harness` / `graff`

## 1. Main Entry Point and Overall Architecture

### Entry Point
- **`src/main.zig:3991`**: `pub fn main(init: std.process.Init) !void` is the program entry point.
- It parses CLI flags, loads API keys from environment, login files, or the macOS keychain, initializes an HTTP client, and then enters one of three modes:

  2. **Interactive REPL**: Reads stdin line-by-line, maintains conversation history, and loops through `Agent.runTurn()`.

## 2. What the Core Zig Binary Does

The binary is a **dual-mode AI agent harness**:

### A. CLI / REPL (`--json` or TTY)
- **Agentic loop**: Reads user input, POSTs to LLM APIs (Anthropic Messages, OpenAI Chat Completions, or OpenAI Responses/Codex), receives tool calls, executes them (in parallel when safe), and feeds results back into the conversation.
- **Built-in tools**: `bash`, `read_file`, `edit_file`, `write_file`, `webfetch`, `codedb`, plus background bash helpers (`bash_output`, `bash_kill`).
- **Meta tools**: `todo_write`, `todo_read`, `ask_user`, `attempt_completion` — handled inline by the orchestrator, not on pool threads.
- **Advanced tools**: `subagent` (spawns isolated child agents) and `workflow` (multi-phase parallel fan-out).
- **MCP integration**: Dynamically discovers and calls tools from `.mcp.json` servers.
- **Permission gating**: Bash and MCP tool calls require user approval unless `/yolo` or `--yolo` is set.
- **Tracing**: Every API call and tool execution is appended to `harness.trace.jsonl`.

### B. HTTP Server (`harness serve`)
- **`src/main.zig:6694`**: `fn serveMain(...)` binds an HTTP/1.1 server (default `127.0.0.1:8787`).
- Each session is a **spawned child** of the same binary running `harness --json`.
- The HTTP bridge speaks **NDJSON** over chunked transfer encoding:
  - `POST /v1/sessions` → spawns child, returns `session_id`.
  - `POST /v1/sessions/{id}` → forwards one JSON protocol line to the child's stdin, streams stdout events back as NDJSON.
  - `DELETE /v1/sessions/{id}` → graceful close.
- CORS is enabled only when a `--token` bearer token is configured (`src/main.zig:6740`).
- The serve protocol is documented in `schema_protocol_json` at `src/main.zig:79`.

### C. One-shot (`-p` / bare prompt)
- Runs a single prompt to completion with no human interaction, outputs final text to stdout, exits.

## 5. Protocol, Streaming, and Stall-Watchdog Logic

### The Streaming Architecture
- **Root (live) requests stream**: When `!self.sub and self.out != null and !self.stream_quiet`, `Agent.request()` calls `postStream()` instead of `postWatched()` (`src/main.zig:7664`).
- **`postStream()`** (`src/main.zig:8760` area):
  1. Sends the HTTP body via `std.http.Client.Request`.
  2. Receives the response head, potentially decompressing (gzip, deflate, zstd).
  3. Reads the SSE/NDJSON response line-by-line in a `while(true)` loop.
  4. Each line is parsed and printed live via `printDelta()` while also being buffered into `full` for later JSON reassembly.

### The Stall-Watchdog (Key Fix)
The codebase explicitly guards against **idle-stall dead connections** (half-open sockets where the server accepts but sends no bytes). This is the "streaming-read stall-watchdog" referenced in the branch. It uses `std.Io.Select` to race I/O against a timeout.

#### `WatchdogFired` enum (`src/main.zig:10587`)
```zig
const WatchdogFired = enum { esc, deadline };
```

#### `stream_stall_ms` (`src/main.zig:10598`)
```zig
const stream_stall_ms: u64 = 120 * 1000; // 2 minutes idle timeout
```

#### Guard Points in `postStream()`

1. **Response-head stall guard** (`src/main.zig:8786`):
   ```zig
   var hsel: Io.Select(HeadDone) = .init(self.io, &hd_buf);
   hsel.concurrent(.head, streamHeadTask, .{&req});
   hsel.concurrent(.stall, streamStallTask, .{self.io});
   ```
   If headers don't arrive within `stream_stall_ms`, the connection is poisoned (`conn.closing = true`) and `error.HungRequest` is returned so the retry loop redials.

2. **Per-line stall guard** (`src/main.zig:8846`):
   ```zig
   var rsel: Io.Select(ReadDone) = .init(self.io, &rd_buf);
   rsel.concurrent(.line, streamLineTask, .{ reader, &line.writer });
   rsel.concurrent(.stall, streamStallTask, .{self.io});
   ```
   If no `\n`-delimited SSE line arrives within 120s, the stream is treated as dead. Same for the "is there more?" peek (`streamPeekTask`) at `src/main.zig:8885`.

3. **Non-streaming POST guard** (`postWatched`) (`src/main.zig:10650`):
   `postWatched` also races `postTask` against `postWatchdog` (200ms ticks, 10-minute hard deadline) so a stuck subagent request cannot wedge a workflow forever.

#### Select Arm Wrappers (`src/main.zig:10609–10638`)
| Task | Role |
|------|------|
| `streamLineTask` | `reader.streamDelimiterEnding(w, '\n')` |
| `streamPeekTask` | `reader.peekByte()` — guards the "more data?" probe |
| `streamHeadTask` | `req.receiveHead(&.{})` — guards header read |
| `streamStallTask` | Sleeps 200ms increments; fires at `stream_stall_ms`; also checks `Agent.esc_cancel` for early Esc abort |

#### Esc-Interrupt During Tools
- `esc_cancel` is an atomic bool (`src/main.zig:8977`).
- `escWatchTask` polls stdin for a bare Esc keypress in a background `Io.async` future while the root awaits tool results (`src/main.zig:8980`).
- Subagents check `esc_cancel` between SSE lines and turn iterations, allowing graceful abort even when no HTTP stream is active.

## 3 Most Load-Bearing Facts

1. **The binary is a self-contained AI agent harness with no external Zig dependencies.** It directly implements a full REPL, HTTP serve bridge, multi-provider LLM client, parallel tool executor, subagent/workflow engine, and MCP client—all in ~13k lines of Zig using only `std` and `std.Io`.
2. **The stall-watchdog is load-bearing for reliability.** Every streaming read (headers, SSE lines, peek-ahead) is raced against a 120-second `Io.Select` deadline. Without it, half-open/dead TLS sockets would hang the agent indefinitely, especially in `--json` / GUI sessions where there is no TTY Esc escape.
3. **`mcp.zig` is the gateway to external tool ecosystems.** The `Registry` spawns stdio servers, serializes JSON-RPC per server via mutex, rewrites `oneOf` to `anyOf` for OpenAI compatibility, and exposes tools to the orchestrator under qualified names (`mcp__<server>__<tool>`).

## 3 Load-Bearing Facts

1. **The entire frontend state is reconciled from backend-issued `SessionSnapshot` DTOs.** The `sessionStore` does not optimistically update messages; it only updates `promptDrafts` and `selection` locally. Every streaming token arrives via Tauri event → `applySessionSnapshot`, which rebuilds `conversationViewsByKey` and timing maps (`sessionStore.ts:315`). This means the frontend is essentially a reactive projection of the backend `RuntimeManager` state.

2. **`WorkspaceBoard` selection state determines the Dockview outer layout, not the other way around.** The board reacts to `selection` (empty / single-chat / saved-workspace) by resetting or restoring the outer Dockview. When the user drags a chat panel in a saved workspace, the layout JSON is serialized and sent back to Tauri (`desktopClient.updateSavedWorkspaceLayout`), and the active chat binding is updated in the store (`WorkspaceBoard.tsx:127`).

3. **The backend spawns a persistent `graff --json` child per conversation and streams JSONL events into `SessionSnapshotDto`s that are pushed to the frontend.** This is the primary bridge: commands are RPC via `invoke`, and live updates are events via `emit_session_updated`. The frontend has no WebSocket or SSE; it relies entirely on Tauri’s `invoke` + `listen` abstraction.

## 3. Runtime (`runtime/simple.rs`)

This is the core orchestrator. It bridges the Tauri frontend to the Zig-native `graff` CLI by spawning persistent `graff --json` child processes per conversation.

**Key structures** (`gui/src-tauri/src/runtime/simple.rs`):

- **`RuntimeManager`** (`L108`) — cloneable, holds:
  - `emitter: Arc<dyn UiEventEmitter>` — pushes `SessionSnapshotDto` to the frontend.
  - `projects: Arc<ProjectStore>` — SQLite registry.
  - `state: Arc<Mutex<RuntimeState>>` — in-memory conversations, workspace list, model selection, pending follow-ups.
  - `sessions: Arc<Mutex<HashMap<String, GraffSession>>>` — live child processes keyed by `conversation_id`.

- **`RuntimeState`** (`L62`) — tracks:
  - `active_workspace_path`, `active_conversation_id`
  - `conversations: HashMap<String, ConversationState>` — messages, titles, request IDs, agent IDs, plan mode, goal.
  - `selected_provider`, `selected_model`, `selected_effort`, `fast_enabled`
  - `model_catalog` — cached result of `graff --schema`
  - `pending_followups` — live `ask_user` prompts awaiting GUI answer.

- **`GraffSession`** (`L97`) — a persistent `graff --json` child:
  - `child: tokio::process::Child`
  - `stdin: Arc<Mutex<ChildStdin>>` — shared so follow-up answers can be injected while a turn is streaming.
  - `reader: Option<Lines<BufReader<ChildStdout>>>` — taken during a turn and returned after.

**Session lifecycle & protocol flow:**

1. **`send_prompt`** (`L416`) — creates a `request_id`, appends a `User` message to `ConversationState`, then calls `stream_turn`.
2. **`stream_turn`** (`L562`) — acquires session IO via `acquire_session_io`:
   - If no session exists, spawns `graff --json --yolo` (with model/agent/mode/effort/fast controls injected) via `spawn_graff_session` (`L1403`).
   - Writes a JSON line `{"type":"user","text":...}` to stdin.
   - Reads JSONL lines from stdout and maps them to DTOs:
     - `text` → `SessionMessageDto::Assistant` (appended incrementally)
     - `reasoning` → `SessionMessageDto::Reasoning`
     - `tool_call` → `SessionMessageDto::ToolStart`
     - `ask_user` → `SessionMessageDto::ToolStart` + stores `FollowupRequestDto` in `pending_followups`
     - `tool_result` → `SessionMessageDto::ToolEnd`
     - `turn` → ends the loop cleanly
     - `error` → pushes `SessionMessageDto::Error` and breaks
   - After each event, calls `emit()` which snapshots state and fires `codegraff://session-updated`.
3. **`send_control`** (`L696`) — sends non-user controls (`set_model`, `set_mode`, `compact`, `set_agent`, `set_effort`, `set_fast`) and waits for an ack JSON line.
4. **`respond_followup`** (`L943`) — writes the structured answer JSON to the session’s stdin, unblocking the streaming loop.
5. **`stop_prompt`** (`L1036`) — kills the session child (`drop_session`), which causes `stream_turn` to hit EOF and finish.
6. **Title generation** (`L355`) — first-turn titles are generated by a fire-and-forget one-shot `graff -p "<title prompt>" --yolo` call.

**Model/provider machinery:**
- `codegraff_binary()` (`L1506`) resolves the engine via a 5-step fallback: `CODEGRAFF_GUI_BINARY` env var → bundled sidecar next to exe → dev build `../../zig-out/bin/graff` → standard install paths (`~/bin/graff`, `/opt/homebrew/bin/graff`, etc.) → bare `graff` on PATH.
- `login_shell_env()` (`L1351`) — on macOS, captures the user’s login shell environment (`env` from `zsh -il`) so `OPENAI_API_KEY` etc. are visible to the GUI-spawned binary.
- `codegraff_schema_models()` (`L1427`) parses `graff --schema` JSON to populate the model picker dynamically.
- Provider auth is handled by mapping to `graff key set`, `graff login`, or direct env var detection. Credentials are deleted from macOS Keychain, `~/.simple-harness-keys.json`, and provider-specific files (`~/.codex/auth.json`, `~/.kimi/credentials/graff-oauth.json`).

**Persistence:**
- Conversations are persisted to `~/.codegraff-gui/conversations.json` (`PersistedConversation`) at turn boundaries (`persist_conversations`, `L783`).
- Prompt settings (provider, model, effort, fast) are persisted to `~/.codegraff-gui/prompt-settings.json` (`persist_prompt_settings`, `L375`).

### What it does
The Python SDK provides two transport variants for driving the harness agent:

## 3. SDK Generation Script (`sdk/generate.py`)

### What it does
`generate.py` is a codegen tool that reads the JSON schema emitted by `graff --schema` and produces all three SDK artifacts:

- `sdk/ts/harness.ts` — Node.js stdio client
- `sdk/ts/remote.ts` — Edge-safe fetch client
- `sdk/py/harness_sdk.py` — Python stdio + urllib client

The script is the **single source of truth** for SDK types; the generated files carry the header `"AUTO-GENERATED by sdk/generate.py from \`harness --schema\`. Do not edit."` (`sdk/generate.py:1`, `sdk/ts/harness.ts:1`, `sdk/py/harness_sdk.py:1`).

### How it works
1. **Schema ingestion** (`load_schema`) accepts:
   - `stdin` (e.g. `graff --schema | python3 sdk/generate.py`)
   - `--schema FILE`
   - `--harness BIN` (runs the binary for you)
   (`sdk/generate.py:16-34`)

2. **Type extraction** pulls three arrays from the schema:
   - `models` → `ModelName` union / `MODELS` constant
   - `tools` → `ToolName` union / `TOOLS` constant
   - `providers` → `ProviderId` union / `PROVIDERS` constant
   - `version` → `HARNESS_VERSION` constant
   (`sdk/generate.py:37-42`, `sdk/generate.py:44-47`, `sdk/generate.py:431-438`)

3. **Template generation** uses large Python f-string templates that embed the sorted unions and version. The templates contain the full class implementations (including telemetry, prompt fingerprinting, score signing, event parsing, etc.). No logic is synthesized from the schema beyond the literal type constants and version string; the rest is static boilerplate maintained inside `generate.py` itself.

4. **Output** writes all three files via `write()` and prints byte counts (`sdk/generate.py:439-445`).

### CI enforcement
The `.github/workflows/sdk.yml` workflow publishes the committed SDKs to npm and PyPI on every `sdk-v*` tag, but the generation must be run locally before tagging because the action does **not** regenerate— it ships what is committed (`sdk/README.md:11-15`, `.github/workflows/sdk.yml:1-8`). The `.github/workflows/ci.yml` also includes a `sdk` job that validates the committed SDKs without requiring a Zig build (`codedb` context for `.github/workflows/ci.yml:10`).

## 4. Relationship to the Broader Project

### Verified facts
1. **The core is a Zig CLI binary.** The project’s engine lives in `src/main.zig` (~1,250 lines of Zig 0.16) and compiles to a single executable named `graff` (formerly `harness`) (`architecture.md:1-3`, `build.zig:32-35`).
2. **The SDKs are thin clients over that binary.** They do not reimplement the agent loop, LLM provider routing, tool dispatch, or context compaction. They only wrap the `--json` stdio protocol or the HTTP bridge (`harness serve`) (`sdk/README.md:1-4`, `sdk/ts/harness.ts:155-157`).
3. **`harness --schema` is the contract.** The Zig binary emits its own interface (models, tools, providers, event protocol, version). The generation script consumes this JSON to keep the SDK types in lockstep with the binary (`sdk/generate.py:1-8`, `sdk/README.md:11-15`).
4. **`harness serve` is an HTTP bridge.** The remote clients do not talk to a separate server implementation. The server side of the bridge still runs the same `harness --json` child per session; one POST equals one protocol request, streamed back as NDJSON (`sdk/ts/remote.ts:1-10`, `sdk/py/harness_sdk.py:338-341`).
5. **The DGM evolution loop is built on the SDK.** `examples/dgm_loop.py` imports `Harness`, `prompt_fingerprint`, and `verify_score` from the Python SDK to implement a Darwin Gödel Machine that mutates system prompts, scores them via a replay judge, and writes lineage into the trajectory archive (`examples/dgm_loop.py:18-20`, `examples/dgm_loop.py:101-110`).
6. **Telemetry is shared.** Both the harness binary and the SDKs report to the same OTLP endpoint (`https://harness-telemetry.rachpradhan.workers.dev` by default) using the same opt-out environment variables (`GRAFF_NO_TELEMETRY`, `OTEL_EXPORTER_OTLP_ENDPOINT`) (`sdk/py/harness_sdk.py:54-96`, `sdk/ts/harness.ts:79-121`).
7. **The CLI was renamed.** The default binary is now `graff`, with `harness` as a fallback compatibility name (`sdk/py/harness_sdk.py:139-142`, `sdk/ts/harness.ts:133-140`).

### Inferred but not directly verified
- The `harness serve` mode is likely implemented inside `src/main.zig` as an HTTP server (referenced in `architecture.md` under “Where this could go next” and in `sdk/ts/remote.ts` comments), but I did not read the Zig server code directly because `src/main.zig` is not indexed by `codedb` in this output.

## Top 3 Load-Bearing Facts

1. **The SDKs are auto-generated from `graff --schema`; the schema JSON is the only source of truth for models, tools, providers, and the event protocol.** Any drift between the binary and the SDKs is caught by regenerating via `sdk/generate.py` (`sdk/generate.py:1`, `sdk/py/harness_sdk.py:1`, `sdk/ts/harness.ts:1`).
2. **Both Python and TypeScript SDKs are thin wrappers: they spawn the local Zig binary (`Harness`) or talk HTTP to a bridge that still spawns the binary per session (`RemoteHarness`).** They do not contain the agent loop, tool implementations, or LLM logic (`sdk/py/harness_sdk.py:148-180`, `sdk/ts/harness.ts:157-167`, `sdk/README.md:1-4`).

## 2. `GraffServeClient.swift` — The NDJSON Protocol Client

### Transport contract
- The client implements the **local `serve` transport** described in `architecture.md` and the TS/Python SDKs (`sdk/ts/remote.ts`, `sdk/py/harness_sdk.py`).
- Two HTTP calls are required per turn:
  1. `POST /v1/sessions` → returns `{session_id}` (`GraffServeClient.swift:47`).
  2. `POST /v1/sessions/{id}` with a JSON payload `{"type": "user", "text": text}` → streamed back as **NDJSON** (one JSON object per line) until a terminal event (`turn` or `error`) (`GraffServeClient.swift:57`).

### Request builder
- `base` defaults to `http://127.0.0.1:8787` (`GraffServeClient.swift:25`).
- Always sends `Content-Type: application/json` and `User-Agent: Graff-iOS/0.1` (`GraffServeClient.swift:33`). The comment explicitly states the UA is required because *"CF WAF rejects empty UA on the gateway path"*.
- Optional bearer token: `Authorization: Bearer <token>` (`GraffServeClient.swift:34`).

### Event decoding
- `GraffEvent` enum (`GraffServeClient.swift:4`) covers:
  - `.reasoning(String)`
  - `.text(String)`
  - `.toolCall(name: String)`
  - `.turn(text: String, contextTokens: Int, costUSD: Double)`
  - `.error(String)`
  - `.other(String)` (fallback for unknown types)
- `decode(_:)` (`GraffServeClient.swift:82`) uses `JSONSerialization` to parse each line and switches on the `type` field:
  - `reasoning`, `text`, `tool_call`, `turn`, `error` are mapped explicitly.
  - Anything else becomes `.other(type)`.

### Streaming implementation
- `streamTurn(sessionID:text:)` returns an `AsyncThrowingStream<GraffEvent, Error>` (`GraffServeClient.swift:57`).
- It uses `URLSession.shared.bytes(for:)` to get an `AsyncBytes` sequence, iterates `bytes.lines`, and yields decoded events.
- **Termination rules**: it stops yielding and finishes the stream when it encounters either `.turn` or `.error` (`GraffServeClient.swift:69-70`).
- Cancellation is wired up: `continuation.onTermination` cancels the `Task` reading the bytes (`GraffServeClient.swift:77`).

### Inferred design note
A code comment (`GraffServeClient.swift:23`) states: *"The `cube` transport is this same client with a different base URL + a tenant capability header."* The current struct only has `base` and `token`; the capability header is not yet implemented.

## 4. Connection to the Core Harness, Data Streamed, and Protocol Handling

### How it connects
- The iOS app targets `http://127.0.0.1:8787`, which is the default address of `graff serve` (or `harness serve`) running on the host Mac.
- Because the iOS simulator shares localhost with the host, `127.0.0.1:8787` from the simulator reaches the host's serve process (`GraffServeClient.swift:20` comment).

### What data streams
- **Request** (turn): `{"type": "user", "text": "<prompt>"}`.
- **Response**: NDJSON lines, each a JSON object. The iOS client specifically handles:
  - `reasoning` → shown in the bubble as a brain-labeled italic caption.
  - `text` → appended to the assistant bubble.
  - `turn` → final text + metadata (`context_tokens`, `cost_usd`). The client replaces the bubble text with the final `turn.text`.
  - `error` → displayed as `"Error: ..."`.
  - `tool_call` → **ignored** (`ChatView.swift:97`).

### Protocol handling characteristics
- **Session-oriented**: A `serveSessionID` is created once per `ChatView` and reused for subsequent turns.
- **Terminal-event driven**: The stream ends on `.turn` or `.error`. This matches the Python/TS SDK behavior (`sdk/py/harness_sdk.py:447`, `sdk/ts/remote.ts:165`).
- **No interactive tool loop**: Unlike the Python/TS SDKs, the iOS client does not currently handle `ask_user` or multi-step `tool_call` / `tool_result` cycles. It treats the stream as a single-turn text response.
- **NDJSON parsing**: Uses `JSONSerialization` (not `Codable`) for line-by-line decoding, which is tolerant of unknown fields.

### Verified cross-reference
The architecture document (`architecture.md`) describes the core harness as a Zig REPL/agent that can run in `--json` mode (stdio) or `serve` mode (HTTP). The iOS client consumes the *serve* bridge, where each session is a real `harness --json` child and one POST equals one protocol request, streamed back as NDJSON (`sdk/ts/remote.ts:8` comment).

## 1. `architecture.md` — Overall System Architecture

**`simple-harness`** (also called `graff`) is a terminal agentic loop implemented in ~1,250 lines of Zig 0.16 with **zero third-party dependencies** — only the Zig standard library (`architecture.md:1-5`). It compiles to a single self-contained executable (~1.69 MB on arm64) that talks to multiple LLM providers, runs tools (including subagents and MCP servers) in parallel, and compacts its own context.

### Core loop (`Agent.runTurn`)
The unit of execution is a single `Agent` struct that owns a message history (`std.json.Array`), a provider, an arena, and the loop methods (`architecture.md:33-37`). The root REPL agent and every subagent are the **same type**; a subagent is just an `Agent` with `sub = true`, a fresh arena, empty history, and `out = null` (`architecture.md:38-40`).

`runTurn` works as follows:
1. `buildBody` serializes the request for the current provider.
2. `post` sends it via the thread-safe `std.http.Client.fetch`.
3. `stepAnthropic` / `stepOpenAI` / `stepResponses` parse the response, echo the assistant turn into history verbatim, collect tool calls, dispatch them via `runTools`, append results, and return either final text (turn done) or `null` (loop again) (`architecture.md:41-48`).

### Providers
The system decouples **wire format** (`Provider.Kind`: `anthropic`, `openai`, `responses`) from **auth style** (`Provider.Auth`: `x_api_key`, `bearer`) (`architecture.md:50-54`). The `provider_specs` table is the single source of truth. Supported providers include anthropic, codegraff, deepseek, openai, minimax, xiaomi, codex (ChatGPT OAuth), and claude (Claude Code OAuth) (`architecture.md:63-73`). `Provider.context` drives per-model compaction at 80% of the context window.

### Streaming
Root-agent requests stream on **all three** wire formats using SSE. `request()` decides per call whether to stream (`live = !sub && out != null && !stream_quiet`). After streaming deltas to the user, the buffered events are **reassembled** into the exact non-streaming response shape so that `step*`, history echo, compaction, and `/save`/`/resume` are untouched (`architecture.md:97-112`).

### Tools
Three kinds, all dispatched through `runTools` (`architecture.md:141`):
1. **Built-in** (`bash`, `read_file`, `edit_file`, `write_file`, `subagent`, `workflow`) — run on the `std.Io` thread pool. `workflow` is dynamic workflows as data: sequential phases of parallel subagents with `{{prev}}` substitution (`architecture.md:142-147`).
2. **Meta** (`todo_write`, `todo_read`, `attempt_completion`, `ask_user`) — handled inline by the orchestrator (`handleMeta`), never on a pool thread. They act on the agent/conversation itself (`architecture.md:148-152`).
3. **MCP** — discovered at runtime from `.mcp.json`, namespaced `mcp__<server>__<tool>`, dispatched to `mcp.Registry.call` (`architecture.md:153-154`).

### Permission model
State-changing tools run behind a shared `Approvals` struct backed by an `Io.Mutex` (`architecture.md:156-157`):
- `gateTool` (root only) covers `bash`, `write_file`, `edit_file`, and MCP calls. Unapproved calls prompt on stdin; approval keys are the bash command's first word or the tool name (`architecture.md:159-162`).
- Subagents are gated structurally: bash is allowlist-only, file writes are path-confined, MCP isn't exposed (`architecture.md:168-170`).
- **Path confinement** (`confinedPath`): file tools reject absolute paths and `..`, confining them to the cwd subtree. This is **not** bypassed by `/yolo` (`architecture.md:175-176`).
- **`/yolo`** lifts the prompt gate and the bash cwd-lock, but never lifts `confinedPath` (`architecture.md:178-179`).

### Parallelism and subagents
`runTools` separates meta calls (inline) from external calls, then fans them out with `io.async` — one `Future` per call — and awaits them in order. Because subagents are external tool calls, three subagents requested in one assistant message run concurrently on the pool, each making its own HTTPS calls through the shared client (`architecture.md:181-187`). Depth is capped at one level; subagents get only the base tool set (no `subagent`, no MCP, no meta tools) (`architecture.md:189-194`).

### MCP client (`src/mcp.zig`)
The harness is an MCP **client**. `Registry.init` reads `.mcp.json`, spawns stdio servers, performs JSON-RPC handshake (`initialize` → `notifications/initialized` → `tools/list`), and registers each tool. It sanitizes schemas by recursively renaming `oneOf` to `anyOf` because OpenAI's validator rejects `oneOf` outright (`architecture.md:224-236`). `Registry.call` serializes `tools/call` behind an `Io.Mutex` because a server is one bidirectional pipe.

### KV-cache and compaction
The loop is structured for prefix cache hits: frozen system prompt, append-only message history, comptime tool-list rendering, and explicit `cache_control: {type: ephemeral}` breakpoints for Anthropic (`architecture.md:248-252`). Compaction is client-side and provider-agnostic: at 80% of the model's context window, the harness sends history plus a handoff instruction with no tools, forces a text summary, and replaces history with one user message embedding that summary (`architecture.md:280-285`).

### Other key features
- **Session persistence**: `/save` serializes `{provider, model, strict, messages}` to `<name>.session.json`; `/resume` parses it back (`architecture.md:257-261`).
- **Lifecycle hooks**: `pre_tool`, `post_tool`, `turn_end` configured in `.harness/settings.json`. `pre_tool` is the only hook with power: exit 2 blocks the call (`architecture.md:290-327`).
- **Tracing**: One shared `Tracer` writes to `harness.trace.jsonl` — one JSON line per event, flushed immediately (`architecture.md:329-334`).
- **Strict mode**: `/strict` forces `tool_choice` so the model must call a tool every turn. Combined with `ask_user` and `attempt_completion`, *every* message is a tool call or tool result (`architecture.md:196-210`).

## 2. `examples/` Scripts — What They Demonstrate

### `dgm_loop.py` — The minimal Darwin Gödel Machine loop
This is a ~110-line runnable proof of the DGM checklist using the Python SDK (`examples/dgm_loop.py:1-12`). It demonstrates:
- **Genome**: a system prompt (auto-captured as `kind:"prompt"` in `harness.trajectory.jsonl`).
- **Archive + lineage**: loaded from `harness.trajectory.jsonl` with `prompt_sha` parent-child edges.
- **Modify**: the harness's own model mutates the parent prompt via `h.ask()`.
- **Evaluate**: uses `replay_eval()` (Step 1 primary gradient) and `llm_tiebreak()` (secondary, capped).
- **Select**: DGM parent selection via `sigmoid(score − frontier) × 1/(1+children)` (`examples/dgm_loop.py:72-84`).
- **Score write-back**: `h.score()` with signed provenance (`judge_id`, `artifact_sha`, `eval_set_hash`) and HMAC verification when `GRAFF_SCORE_KEY_FILE` is set (`examples/dgm_loop.py:144-148`, `148-161`).

It uses `Harness(yolo=True)` from `sdk/py/harness_sdk.py` and spawns subagents with per-child `system_prompt` overrides.

### `replay_judge.py` — Step 1: Grounded, out-of-process evolution judge
This is the primary fitness gradient. It runs a candidate system prompt against a held-out eval set of tasks with **deterministic assertions** — a shell command's exit code or a golden substring in the final report (`examples/replay_judge.py:1-12`). Key properties:
- **Custody**: the eval set lives outside the editable tree (`GRAFF_EVAL_SET_FILE`); its sha256 is pinned (`GRAFF_EVAL_SET_HASH`). Hash mismatch → exit 3, fail-closed (`examples/replay_judge.py:35-51`).
- **Hermetic**: each task runs in a fresh scratch directory so file assertions are isolated (`examples/replay_judge.py:93-96`).
- **Speaks `--json` directly**: dependency-free, no SDK import; it drives `graff --json --yolo` as a subprocess and parses the NDJSON stream (`examples/replay_judge.py:55-91`).
- **Efficiency gradient**: counts `tool_calls` and `cost` so once all tasks pass, economy (fewer tool calls) discriminates winners (`examples/replay_judge.py:123-130`).

### `test_step1.py` — Proof obligations for the grounded judge
Offline tests (no model calls) verify structural invariants (`examples/test_step1.py:1-12`):
1. **Score-band invariant**: a variant failing ANY held-out task can never reach the promotable band (≥ 0.9). The worst gap is verified to be > 0 (`examples/test_step1.py:38-42`).
2. **Fail-closed**: replay judge missing → score 0.0 (`examples/test_step1.py:44-48`).
3. **Integrity exits**: missing eval set → exit 2; hash-pin mismatch → exit 3 (`examples/test_step1.py:56-64`).
4. **Live Goodhart rejection**: a sabotage variant that claims success but does nothing gets a high `h.ask` score, yet `judge()` pins it ≤ 0.8 because the replay suite fails. An honest seed reaches ≥ 0.9 (`examples/test_step1.py:67-86`).

### `edge-worker/` — Remote SDK in Cloudflare Workers
Proof that the remote SDK runs in the real Workers runtime (`workerd`), where the native harness binary cannot run (`examples/edge-worker/README.md:1-4`). It demonstrates:
- `src/remote.ts` is a vendored copy of `sdk/ts/remote.ts` (auto-generated from `harness --schema`), using **fetch + Web Streams only** — no `node:` imports (`examples/edge-worker/src/remote.ts:1-5`).
- `src/index.ts` shows two modes: a default multi-turn session + one-shot, and a streamed one-shot turn via `?q=` query param (`examples/edge-worker/src/index.ts:12-36`).
- The bridge is `harness serve` running elsewhere; `BRIDGE_URL` and `BRIDGE_TOKEN` are configured via env/secrets.

## 3. `docs/` — Design Decisions and Future Plans

### `hyperagents.md` — Swarm trajectories & the path to hyperagents
- **Prompt heterogeneity**: the swarm now supports per-child `system_prompt` overrides (precondition for DGM-style evolution) (`docs/hyperagents.md:1-18`).
- **Trajectory mapping**: `harness.trajectory.jsonl` holds DGM-archive-tree nodes (`kind:"turn"`, `"subagent"`, `"prompt"`, `"score"`) with `parent`, `prompt_sha`, `prompt_mutated`, and `task` fields (`docs/hyperagents.md:19-42`).
- **Internal DGM-H design**: the loop itself belongs in SDK code (Python/TS), not the harness. The harness exposes primitives: editable program (`set_system_prompt`), modify (`subagent`/`workflow` with override), evaluate (driver-owned judge), archive (`trajectory.jsonl` + scores), and selection (`sigmoid(...) × 1/(1+children)`) (`docs/hyperagents.md:43-82`).
- **MAP-Elites**: niches = agent types (e.g. reviewer, researcher). Elites live at `.harness/agents/<niche>.md` — one markdown per cell with frontmatter (`name`, `description`, `score`). The driver promotes challengers that beat the incumbent score (`docs/hyperagents.md:83-112`).
- **Step 0 — Signed fitness channel**: HMAC-SHA256 over a canonical message (`v1\n{prompt_sha}\n{parent_sha}\n{score:.6f}\n...`) so forged score rows are detectable. Key lives outside cwd; verification is fail-closed (`docs/hyperagents.md:113-145`).
- **Step 1 — Grounded replay judge**: held-out replay eval with deterministic assertions. Score bands: fail → 0.0; pass_rate < 1.0 → capped at 0.8; all pass → 0.9 + 0.1×efficiency. LLM tie-break only reorders already-passing variants (`docs/hyperagents.md:146-173`).
- **Step 2 — Federated fleet evolution**: scaffolded but not fully built. The fleet is the archive. Thousands of installs generate/evaluate variants on their own providers. Central infra (`harness-telemetry` worker) does only cheap work: HMAC-verify, artifact re-check, SQL-aggregate, serve elites. Data model includes `harness_elites` table and `GET /v1/elites` endpoint (`docs/hyperagents.md:174-258`).

### `install-flow.md` — Diagnosis & fix
Documents a bug in the `curl | sh` install path (`docs/install-flow.md:1-3`):
- **Root cause 1**: tarball layout mismatch. CI nests the binary under `graff-<target>/`, but hand-repacked macOS tarballs ship it flat. `fetch_release` assumed nested, failed with `No such file`, and because it ran inside `if ...`, `set -e` was suppressed, so it returned `rm -rf`'s status (0) and falsely reported "ok" (`docs/install-flow.md:20-28`).
- **Root cause 2**: companion step called `codegraff.com/install-graff.sh` (the harness installer) instead of `codegraff.com/install.sh` (the tools installer), causing infinite recursion and hang (`docs/install-flow.md:29-33`).
- **Fix**: robust binary location handling both flat and nested layouts, explicit `return 1` if binary didn't land, correct companion URL, and `curl --max-time 120` bound (`docs/install-flow.md:35-43`).

### `memory-architecture.md` — First-class, evolvable memory layer
- **Hard constraint**: memory must be **append-only context**, never prefix mutation, to preserve the KV-cache (`docs/memory-architecture.md:1-22`).
- **MemoryDesign interface**: the evolvable unit with `retrieve`, `update`, and optional `eval` vtable. Fingerprinted (`memory_sha`) like prompts (`docs/memory-architecture.md:23-38`).
- **Built-in designs**: `null`, `scratchpad`, `episodic`, `structured`, `engram`, `summary-tree`. File-backed under `.harness/memory/` by default; `engram` is an optional MCP upgrade (`docs/memory-architecture.md:39-58`).
- **Scopes**: `session` (arena), `project` (cwd), `user` (`~/.simple-harness/memory/`), `fleet` (shared, evolved). Fleet scope requires a **code-execution gate** because an evolved memory Design is code that runs (`docs/memory-architecture.md:59-82`).
- **Evolution**: coordinate-ascent with DGM (mutate persona) and ALMA (mutate memory design). Memory designs are evaluated on long-horizon tasks with outcome-only credit (`docs/memory-architecture.md:83-95`).

## 4. `packages/diffs/` — What It Does and GUI Integration

### Package purpose
`@codegraff/diffs` is a **lightweight, dependency-free diff and file-change rendering package** with no Shiki dependency (`packages/diffs/package.json:1-4`). It is built as an ESM module with TypeScript, managed by bun.

### Core modules
- **`parse.ts`** (`packages/diffs/src/parse.ts`): Parses git-style unified diffs into a structured `ParsedPatch` model (`FileDiff[]`, `DiffHunk[]`, `DiffLine[]`). Tolerant of partial/synthetic patches; normalizes CRLF; handles `diff --git`, `new file mode`, `deleted file mode`, binary files, and hunk headers (`@@ -l,s +l,s @@`). Tracks per-file and total `additions`/`deletions` stats.
- **`highlight.ts`** (`packages/diffs/src/highlight.ts`): A tiny, dependency-free syntax tokenizer per line. Supports 11 languages (`ts`, `js`, `py`, `rs`, `go`, `zig`, `json`, `css`, `shell`, `md`, `plain`). Tokenizes into `keyword`, `string`, `comment`, `number`, `punct`, `plain`. Per-line only — multi-line strings/comments are not tracked.
- **`wordDiff.ts`** (`packages/diffs/src/wordDiff.ts`): Intra-line word diff using LCS (longest common subsequence). Splits lines into word-ish tokens, then computes `DiffSegment[]` (`same`/`added`/`removed`). Has a **200,000 cell budget**; if the LCS table would exceed that, it bails out to a single removed/added segment to avoid hanging/OOMing the tab during render.
- **`types.ts`** (`packages/diffs/src/types.ts`): Shared TypeScript interfaces for `DiffLine`, `DiffHunk`, `FileDiff`, `ParsedPatch`, `DiffSegment`, `DiffStats`.

### React components
- **`PatchDiff.tsx`** (`packages/diffs/src/react/PatchDiff.tsx`): Top-level component. Takes a raw git patch string, parses it with `useMemo(parsePatch)`, and renders a list of files with optional file headers and stats badges (`added`/`deleted`/`renamed`).
- **`DiffBody.tsx`** (`packages/diffs/src/react/DiffBody.tsx`): Renders the body of a single file. Applies **word-level intra-line diffing** by pairing consecutive deletion/addition runs and running `diffWords()` on each pair. Renders hunks with line numbers, `+`/`-`/`` signs, and syntax-highlighted content via `tokenizeLine`. For `DiffSegment` lines, it renders only the side that owns the change (e.g., `removed` spans only on the before side, `added` only on the after side).
- **`FilesChanged.tsx`** (`packages/diffs/src/react/FilesChanged.tsx`): A collapsible file list. Each row shows path, badge, stats, and a toggle caret. Clicking expands to show the `PatchDiff` for that file. Uses `memo` for row performance.

### Styling
- `src/style.css` provides the base CSS classes (`cgd-root`, `cgd-file`, `cgd-line`, `cgd-gutter`, `cgd-word`, `cgd-tok`, etc.) (`packages/diffs/src/style.css`).
- The GUI imports the style in `gui/src/main.tsx` (`import '@codegraff/diffs/style.css'`) and binds theme tokens in `gui/src/styles/diffs.css` so diffs adapt to light/dark mode.

### GUI integration
The package is used in two main GUI locations:

1. **Chat activity results** (`gui/src/components/chat/activity-results/FileDiffResult.tsx:3`): Imports `PatchDiff` from `@codegraff/diffs/react`. Displays a file diff inside an `ActivityResultCard` with an "open in editor" button. Uses `options={{ lineDiffType: "word", showFileHeader: false }}` (`gui/src/components/chat/activity-results/FileDiffResult.tsx:91-95`).
2. **Workspace changes pane** (`gui/src/components/workspace-board/ChangesPane.tsx:11`): Imports `PatchDiff` to render session file changes in a collapsible sidebar. Each `ChangeRow` uses `Collapsible` to expand/collapse the diff. Also uses `lineDiffType: "word"` and `showFileHeader: false` (`gui/src/components/workspace-board/ChangesPane.tsx:88-94`, `176-180`).

The GUI's `package.json` declares `"@codegraff/diffs": "workspace:*"` and has a `"build:deps"` script that builds the diffs package first (`gui/package.json:11`, `20`).

**`graff`** (formerly `simple-harness`) is a self-contained AI agent harness implemented as a single Zig executable with **zero third-party dependencies**. ## 3. Data Flow / Protocol

### Universal Protocol: JSONL / NDJSON
Whether over stdio or HTTP, the protocol is line-delimited JSON. A parent sends a user turn as one JSON object (`{"type":"user","text":"..."}`) and reads a stream of events until a terminal `.turn` or `.error`.

**Event kinds** (consumed by all frontends):
- `text` → assistant token delta
- `reasoning` → thinking block
- `tool_call` / `tool_result` → tool lifecycle
- `ask_user` → interactive follow-up prompt
- `turn` → turn complete (final text + metadata)
- `error` → fatal turn error

### Mode 1: Local stdio (GUI, Python/TS `Harness`, SDK local)
1. Parent spawns `graff --json --yolo` as a persistent child (`gui/src-tauri/src/runtime/simple.rs:1403`, `sdk/py/harness_sdk.py:175`, `sdk/ts/harness.ts:165`).
2. Parent writes one JSON line to `stdin`.
3. Child streams NDJSON lines to `stdout`.
4. Parent parses lines into DTOs and either emits Tauri events (GUI) or yields to the caller (SDKs).

### Mode 2: HTTP bridge (`graff serve`, Remote SDKs, iOS)
1. `graff serve` binds an HTTP/1.1 server (`src/main.zig:6694`).
2. Client `POST /v1/sessions` → receives `session_id`.
3. Client `POST /v1/sessions/{id}` with one JSON payload.
4. Server forwards to a spawned `graff --json` child and streams the child's stdout back as NDJSON over chunked transfer encoding (`src/main.zig:6920`).
5. CORS is enabled only when a `--token` bearer is configured (`src/main.zig:6740`).

### Mode 3: Internal LLM streaming (Zig core)
Inside `Agent.runTurn()`, the core POSTs to the provider via `std.http.Client` and parses SSE/NDJSON responses. Every streaming read is raced against a **120-second stall-watchdog** using `Io.Select` to poison half-open connections (`src/main.zig:8786`, `src/main.zig:8846`, `src/main.zig:10598`).

### GUI-specific push flow
The Tauri `RuntimeManager` emits a full `SessionSnapshotDto` on **`codegraff://session-updated`** after every single JSONL event (`gui/src-tauri/src/runtime/simple.rs:1181`, `gui/src-tauri/src/bridge/emitter.rs:12`). The React frontend listens to this event and calls `applySessionSnapshot()`, which rebuilds the entire Zustand conversation state from scratch (`gui/src/app/sessionStore.ts:315`). The frontend never holds authoritative message state.

## 5. Key Patterns and Design Decisions

| Pattern | Description | Evidence |
|---|---|---|
| **Zero external dependencies (core)** | The Zig binary uses only `std` (and an internal `std.Io` abstraction). SDKs use only language stdlibs. | `build.zig` (no `build.zig.zon`), `sdk/py/harness_sdk.py` (no `requests`), `sdk/ts/remote.ts` (no `node:`) |
| **Backend owns state; frontend is reactive** | The GUI does not optimistically update messages. It waits for `SessionSnapshotDto` and rebuilds. | `gui/src/app/sessionStore.ts:315`, `gui/src-tauri/src/runtime/simple.rs:1181` |
| **Schema-driven SDK lockstep** | `graff --schema` is the API contract. SDK types are regenerated so they never drift from the binary. | `sdk/generate.py:1`, `sdk/README.md:11` |
| **Persistent child-per-conversation** | The Tauri backend and local SDKs keep one `graff --json` subprocess alive per conversation, reusing it across turns. | `gui/src-tauri/src/runtime/simple.rs:1057`, `sdk/py/harness_sdk.py:175` |
| **Stall-watchdog on every streaming read** | `Io.Select` races HTTP response headers, SSE lines, and peek-ahead probes against a 120-second deadline. | `src/main.zig:8786`, `src/main.zig:8846`, `src/main.zig:10598` |
| **Path confinement + permission gating** | File tools are confined to cwd; bash and MCP require user approval unless `/yolo` is active. | `architecture.md:175`, `src/main.zig:10695` |
| **DGM evolution primitives** | The binary exposes `set_system_prompt`, `subagent`, and `score()`. The DGM loop lives in SDK driver code, not the core. | `docs/hyperagents.md:43`, `examples/dgm_loop.py:1` |
| **Auto-compaction with handoff** | At 80% context window, the harness forces a summary turn and replaces history with it to preserve KV-cache prefix. | `architecture.md:280`, `src/main.zig:7461` |

## Verified vs. Inferred

**Verified**
- The Zig core is a single executable with no external Zig dependencies (`build.zig`, `src/main.zig`).
- The Tauri backend spawns `graff --json` per conversation and speaks JSONL over stdio (`gui/src-tauri/src/runtime/simple.rs:562`, `simple.rs:1403`).
- The GUI frontend rebuilds state exclusively from `SessionSnapshotDto` pushed by the backend (`gui/src/app/sessionStore.ts:315`, `gui/src-tauri/src/bridge/emitter.rs:12`).
- The SDKs are auto-generated from `graff --schema` (`sdk/generate.py:1`, `sdk/ts/harness.ts:1`).
- The iOS app consumes the HTTP `serve` bridge and ignores `tool_call` events (`GraffServeClient.swift:69`, `ChatView.swift:97`).

**Inferred**
- The `std.Io` abstraction used for async I/O in the Zig core is a custom/patched runtime layer, not standard Zig 0.16/0.17 (`docs/zig-0.17-port-plan.md:8`). Its exact origin and maintenance plan are undocumented in the repo.
- The DGM federated fleet loop (Step 2) is scaffolded in docs and SDKs but not yet fully implemented (`docs/hyperagents.md:174`).
- The `MemoryDesign` interface described in `docs/memory-architecture.md` is a design proposal; it is not yet implemented in the Zig source.

## 3 Most Load-Bearing Facts

1. **The entire system is a thin wrapper around a single self-contained Zig binary.** The GUI, SDKs, and iOS app all consume the same JSONL/NDJSON protocol emitted by `graff --json` (stdio) or `graff serve` (HTTP). The core itself has zero external dependencies and implements the full agentic loop, multi-provider streaming, parallel tool execution, and MCP client discovery.
2. **The GUI frontend is a stateless reactive projection of the Tauri backend.** The React Zustand store never optimistically updates conversation state; it only applies `SessionSnapshotDto` payloads pushed via `codegraff://session-updated`. The backend, in turn, only wraps a persistent `graff --json` child process per conversation. This means the frontend is effectively a remote renderer for the Zig core's stdout.
3. **The project embeds a full Darwin Gödel Machine (DGM) evolution loop** with schema-driven SDK generation, HMAC-signed fitness scores, and a grounded replay judge that uses deterministic assertions to prevent LLM "charming." However, the GUI and iOS app do not yet consume the federated fleet telemetry endpoints (`pull_elites`, `score`), leaving the visual layer disconnected from the evolution infrastructure.
