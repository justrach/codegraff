Different tool philosophies

Graff reaches for its code index (codedb, codedbpro MCP) and shells out for confirmation; kimi-cli relies on bare Grep/Read and makes 3× fewer tool calls. Both strategies converge on the same correct facts.

Round 1 → Round 2

Round 1 (pre-fix build): graff 389.3s total vs kimi 222.8s true-turn, dragged by a 221s MCP-latency outlier on providers. Round 2: that outlier collapsed to 60.7s; kimi's times also dropped (warm server-side prompt cache — 65–141k cache-read tokens per turn).

The fix this benchmark surfaced

Round 1 showed graff badging "k3 · Medium" while kimi-cli ran K3 at thinking=high — an apparent effort mismatch that would have invalidated the comparison.

  • It was a badge bug, not a behavior bug. Graff's Kimi request path normalizes the session effort through the catalog allow-list (pricing.kimiThinkingEffort); the wire had always carried the catalog default. The live server declares K3 default_effort: "high" — the same effort kimi-cli used. Efforts were equal all along; only the status line lied.
  • Fix: src/agent_prompt.zig now badges the normalized wire effort (effectiveEffort), and the baked K3 catalog row in src/pricing.zig was updated from ["max"] to the server's real allow-list [low, high, max] (default high) so /effort low|high work offline too.
  • Verified live: round 2's graff prompt reads [k3 · High · kimi …] — display matches the wire, and the comparison above is effort-matched by construction.
  • 1208 unit tests green (baseline 1184), including a new regression test pinning the badge normalization.

Where the time goes (instrumented)

From graff's own run traces (.graff/traces/*.jsonl) and kimi-cli's wire log — no guessing.

  • Tool execution is free; model round-trips are everything. Across every graff run, total tool time was 0.1–0.2s per task (codedb and even the codedbpro MCP calls answer in <100ms). 99%+ of wall time is API latency: ~5–9s per call at thinking=high.
  • Graff makes 2–3× more model calls than the task needs. runEval: 14 calls vs kimi's 6 for the same correct answer. Each avoidable round-trip costs ~8s at high effort — that gap is the headline speed difference, not tool quality.
  • Round 1's 221s outlier was a stalled stream, not MCP. The trace shows the first model call hung ~127s before the stall watchdog (default 120s, GRAFF_STREAM_STALL_SECS) killed and retried it; the call then completed in 6s. MCP was blamed in round 1's interim report — the traces say otherwise.
  • Title generation is off the critical path. The AI tab-title call (~3s) fires concurrently with turn 1 and costs no wall time.

Outlier hunt — one pass, no reruns

A trace analyzer (analyze_outliers.py) reads each run's event log once and localizes every anomaly: any call >2× the run's median, plus stall-retry events. Ran over all 13 graff traces and 13 kimi sessions from every round.

  • Final-call outliers are benign. Nearly every run's last call flags at 2–3× median — that's the model writing the long final answer, not a fault. Any outlier that isn't the last call deserves the look.
  • Graff's stall watchdog earns its keep. Round 1's 221s task: first stream hung, watchdog killed it at ~127s, retry finished in 6s. The analyzer flags the stream_retry event directly.
  • Kimi-cli has no equivalent protection — caught live. In the repetition batch, kimi's 2nd request on providers-r2 hung silently for 343.5s (5.7 min) before the server answered; the turn took 378.7s for a question it otherwise answers in 29–39s. No retry, no warning.
  • Mid-turn blowups mark the low-effort pathology. graff's permgate-low run flags calls #12/#13 at 6.5×/8.3× median (30s/38s) — the signature of low effort trading thinking for extra round-trips.
  • Every run pays a refusal dance. The model's first move is the native codedb tool, which the licensed codedb-pro guard refuses, forcing a load_tool_schemas discovery round-trip before real work starts — ~2 calls ≈ 8–12s per task. The fix needs no code: GRAFF_MCP_EAGER=codedbpro (src/mcp_schema_gate.zig:79) preloads the schemas, so the model calls the pro tools directly. Making eager the default when a licensed in-charge server connects is a ~5-line change in that (unowned) file.
  • Gotcha found — both harnesses persist effort. Kimi-cli keeps /effort across sessions in its own state; graff persists it to .harness/settings.json in the cwd. The repetition batch meant for high effort silently ran at low on BOTH sides (symmetric, so the A/B held — but the label was wrong until the traces outed it).

Improvement roadmap — with projections from this data

P1 · Tool-call economy shipped: best run 32.6s

Projection tested with a prompt-level economy nudge on runEval: when K3 economizes, the run drops to 6 calls / 40.3s — but the nudge only landed ~50% of the time, and K3 emitted zero parallel tool batches across all 15 runs, so economy had to be systemic, not advisory. The systemic fix: the tool-result handle threshold (tool_handle.zig, #440) was 4 KiB, so nearly every search/read came back as a handle that cost a follow-up round-trip. Raised to 16 KiB (still bounded, still clamped by the per-output cap, env-tunable via GRAFF_TOOL_HANDLE_BYTES). Stock-binary validation on runEval (low effort, per the persistence note below): 9 calls / 64.8s and 6 calls / 32.6s — the fastest graff run recorded, edging kimi-cli's best low-effort true turn (33.9s), answer correct. 1209 tests green.

P2 · Effort routing shipped

src/effort_route.zig: a lookup-shaped prompt (question cue, no mutation verb) runs its turn at low effort while the session knob is the untouched default — explicit /effort always wins. The cue list is pinned against the benchmark tasks themselves: runEval and providers route low, permgate (which inflated +85% at low) stays high. Shipped with a regression test.

P3 · Faster stall recovery shipped

With thinking streamed, a socket silent for >45s before the FIRST token is dead, not reasoning — so the pre-token budget is now capped at 45s (http_stall.head_ceiling_ms, env-overridable via GRAFF_STREAM_HEAD_STALL_SECS; GRAFF_STREAM_STALL_SECS still wins both regimes when set). Graff's own stalled task would have capped at ~95s instead of 221s — and kimi-cli's silent 343.5s hang has no equivalent protection at all.

Done · Cache lease first calls 0 → 10k warm

Kimi partitions its prompt cache by prompt_cache_key, and graff minted a fresh UUID per process — so every session's first call was cache-cold while kimi-cli's hit ~19k warm. The kimi path now sends a durable per-project key (http_headers.projectCacheKey, cwd-derived UUIDv5). Measured: first-call cache_read went 0 → 9.7–10.1k on back-to-back sessions.

Done · Effort badge honesty

The badge now names the effort that goes on the wire (effectiveEffort), and the baked K3 catalog matches the server's [low, high, max] allow-list. Shipped in this working tree; 1208 tests green.

Method & caveats

  • Same everything: model (K3), auth (one Kimi Code OAuth subscription), working tree (git archive of HEAD into a clean fixture, no MCP config), prompts (verbatim from benchmarks/tasks.py), permission mode (--yolo both), fresh session per cell.
  • Interactive for real: both TUIs driven through a PTY (scripts/pty_harness.py). Graff turn end = prompt return (exact); kimi turn end = 20s output silence, so its wall times carry a fixed ~21s pad — judge kimi by the "true turn" column from its own session log.
  • One run per cell per round. Timings swing with network and server-side cache warmth (kimi round 2 read 65–141k cached tokens per turn). Treat ratios as directional, not absolute.
  • Read-only Q&A tasks only. No editing, refactoring, or multi-step agentic work is measured here.
  • Found while automating: kimi-cli's TUI swallows Enter sent in the same write() as the prompt text (paste detection) — automation must send text, pause, then Enter. Also, it self-upgraded 0.26.0 → 0.34.0 on launch without asking.
